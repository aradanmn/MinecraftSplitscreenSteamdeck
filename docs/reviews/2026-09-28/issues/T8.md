## Summary

`tests/lib/uhid_pad.py:379-381` (`UhidPad.axis`) writes the value into `self._axes` and only then calls `send()`, where `encode_report` (`:264-266`) range-checks it and raises. The bad value is already committed, so every later `send()` — from `press`, `release`, `hat`, `hold` — re-encodes the poisoned axis and raises again. `_run_command_loop` (`:445-447`) catches the error, prints `bad command`, and continues, so the pad stays alive but is dead for the rest of its life (`neutral` is the only recovery, because it clears before sending). `press`/`hat` validate before mutating; `axis` is the odd one out. `tests/lib/fake_pad.sh` (the CI double) rejects out-of-range axes *without* state change, so `test_uhid_rig.sh` cannot see this — the drift guard only compares `--help` text.

## Evidence

```python
# tests/lib/uhid_pad.py:379-381
    def axis(self, name, value):
        self._axes[normalize_axis(name)] = int(value)   # stored BEFORE the range check
        self.send()                                      # encode_report raises here
```

Reproduced in-process against the pristine module (no `/dev/uhid` needed — the exception fires before the write):

```
axis: axis LX out of range: 300
_axes after: {'LX': 300}
press BTN_SOUTH: axis LX out of range: 300
```

## Failure scenario

A rig script sends `axis LX 300` by typo → all later `press BTN_SOUTH` acks turn into `bad command 'press BTN_SOUTH': axis LX out of range: 300`; the operator reads it as a button-name problem and debugs the wrong thing for a Deck session.

## Suggested fix

Validate before storing (same discipline as `press`/`hat`), and add a `--self-test` line that exercises `UhidPad.axis` on an un-created pad so the bash suite can assert it in CI.
