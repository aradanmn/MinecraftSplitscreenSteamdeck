## Summary
`install-minecraft-splitscreen.sh:90` registers `trap cleanup EXIT INT TERM`. The INT/TERM handler is `cleanup` alone — it never re-raises or exits. Bash semantics: after a trap handler returns, the script resumes. Aborting therefore depends on `set -e` seeing a non-zero status, which the installer deliberately shields everywhere: the `set +e` window in `download_modules` (`:181-239`), every `|| true` / `if cmd` guard, and every prompt — `mcss_prompt` (`modules/utilities.sh:329-332`) treats a failed `read` as EOF and takes the default answer. Meanwhile `cleanup` has already `rm -rf`'d `MODULES_DIR`, so `install_runtime_modules()` (`modules/runtime_deploy.sh`) misses tier 1 and re-downloads modules from GitHub `main` instead of deploying the checkout the user ran.

## Evidence
```bash
# install-minecraft-splitscreen.sh:82-90
cleanup() {
    if [[ -n "$MODULES_DIR" ]] && [[ -d "$MODULES_DIR" ]]; then
        echo "🧹 Cleaning up temporary modules..."
        rm -rf "$MODULES_DIR"
    fi
}
trap cleanup EXIT INT TERM
```
Reproduced with the real installer + real modules and a stub `main()` that blocks on a `read` (the shape of every `mcss_prompt`): after `kill -INT <pid>` the log shows `MAIN_START`, then `🧹 Cleaning up temporary modules...`, and the process is still alive at the prompt five seconds later with `MODULES_DIR` gone (T7.19 on the pristine script: `verdict=alive; cleanup ran=1`). With `timeout`'s SIGTERM the behaviour is identical.

## Failure scenario
`./install-minecraft-splitscreen.sh` from a feature-branch checkout; the user hits Ctrl-C at the "Add to Steam?" prompt to abort. The trap deletes the module dir, the prompt takes its default, the install continues, and the deployed `modules/` come from GitHub `main`, not the checkout — exactly the drift `deploy.sh` exists to catch.

## Suggested fix
Keep `cleanup` on EXIT; make INT and TERM clean up and then *terminate* with the conventional 128+signal codes, disarming the EXIT trap so cleanup does not run twice.

+# the script at the next statement, and this script deliberately shields
+# many commands from set -e (the set +e window in download_modules, `|| true`
+# guards, and every mcss_prompt — whose EOF fallback makes a Ctrl-C at a
+# prompt look like "use the default"). With the old `trap cleanup EXIT INT
+# TERM`, Ctrl-C deleted MODULES_DIR and the install carried on, and
+# install_runtime_modules then silently re-downloaded modules from GitHub
+# instead of deploying the checkout's. Exit with the conventional 128+signal
+# codes; `trap - EXIT` stops cleanup running a second time.
+trap cleanup EXIT
+trap 'cleanup; trap - EXIT; exit 130' INT
+trap 'cleanup; trap - EXIT; exit 143' TERM

Why this is correct: `trap 'cleanup; trap - EXIT; exit 130' INT` is the standard bash idiom — the handler runs, the EXIT trap is disarmed (cleanup already ran), and the process exits with 130/143 so a parent (`run_with_spinner`, a hardware stage, CI) sees the interruption. `cleanup` itself is unchanged. Deliberately NOT changed: `mcss_prompt`'s EOF default (correct for a genuine EOF; it just must never be reached by Ctrl-C), the `set +e` window in `download_modules`, and `install_runtime_modules`' network fallback (the fallback is fine — it must simply not be triggered by an aborted run).
