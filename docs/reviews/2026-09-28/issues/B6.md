## Summary
For an existing instance, `create_instances` calls `handle_instance_update` (`modules/instance_creation.sh:207-209`), which seds `instance.cfg`, calls `install_fabric_and_mods … true` (`:839`, instance 1 downloads EVERY mod), restores options.txt and writes mmc-pack.json. `create_instances` then overwrites `instance.cfg` from the fresh heredoc (`:225-243`) — throwing away the sed edits and any user customisation such as a hand-tuned `JvmArgs`/`MaxMemAlloc`, contradicting "Your existing settings and preferences will be preserved" (`:787`) — rewrites mmc-pack.json (`:251`) and calls `install_fabric_and_mods` a second time (`:280`). Because the first call runs inside `$(…)`, its `MISSING_MODS+=` additions are lost in the subshell.

## Evidence
`modules/instance_creation.sh:207-209`, `:280`, `:839`:
```bash
preserve_options_txt=$(handle_instance_update "$instances_dir/$instance_name" "$instance_name")
...
cat > "$instance_dir/instance.cfg" <<EOF          # :225 — clobbers the sed edits above
...
install_fabric_and_mods "$target_instance_dir" "$instance_name" "$preserve_options_txt"   # :280 — second run
...
install_fabric_and_mods "$instance_dir" "$instance_name" true   # :839 — first run, inside $( )
```
Reproduced with T8.1 below against the pristine module: with `install_fabric_and_mods` stubbed to record calls, a 2-instance update records `latestUpdate-1:true latestUpdate-1:true latestUpdate-2:true latestUpdate-2:true` and `JvmArgs=-Xcustom` is replaced by the default flag set.

## Failure scenario
4-instance update with 12 mods: 24 Modrinth/CurseForge downloads instead of 12, "Downloading mods for first instance..." printed twice, a user's custom `JvmArgs`/`MaxMemAlloc` silently reset, and any mod that failed only in the first run is missing from the final summary.

## Suggested fix
Make `handle_instance_update` do only what its name says (clear mods, edit `instance.cfg` in place, report whether options.txt exists) and drop its `install_fabric_and_mods`/`write_mmc_pack_json`/backup-restore; on the update path skip the `instance.cfg` heredoc (the in-place edit already ran), adding the two installer-owned JVM keys the heredoc would have written only when they are absent.

**Fuller fix:** route the in-place edits through `setInstanceCfgValue` (instance_lifecycle.sh already escapes `&`/`|`) via a guarded `type` check, so the update path has one cfg writer and B26 disappears with it.
