## Summary
`setup_splitscreen_launcher_script` (`modules/runtime_deploy.sh:65-83`) downloads straight onto the live `$TARGET_DIR/minecraftSplitscreen.sh` and, when the result is not a script, `rm -f`s it. `install_runtime_modules` (`:170-185`) likewise `cp`/`fetch_url`s each module directly to `$TARGET_DIR/modules/<mod>`. `curl -o` truncates its target before the transfer starts, so a 404 (bad `REPO_REF`), a mid-transfer drop, or a `--max-time` expiry replaces a previously working install with an empty launcher (then deleted) and/or a partial module, and the installer aborts (`main_workflow.sh:172-173`) leaving the Steam shortcut pointing at nothing.

## Evidence
```bash
# runtime_deploy.sh:72-82
fetch_url "$remote_script" "$launcher_script" || true
...
if [[ ! -s "$launcher_script" ]] || ! head -n1 "$launcher_script" | grep -q '^#!'; then
    ...
    rm -f "$launcher_script" 2>/dev/null || true
    return 1
```
Reproduced (fixture: a working launcher + `modules/orchestrator.sh` under `TARGET_DIR`; `fetch_url` stubbed to write an empty file / a truncated body and fail):
```
== ORIGINAL
[FAIL] T7.22a launcher was ls: cannot access '.../PolyMC/minecraftSplitscreen.sh': No such file
[FAIL] T7.22b: # TRUNC   (live orchestrator.sh now holds the partial body; watchdog.sh appeared empty)
== PATCHED
[PASS] T7.22a failed launcher fetch leaves the working launcher in place
[PASS] T7.22b failed module download leaves live modules untouched
[PASS] T7.22c no staging leftovers
```

## Failure scenario
`REPO_REF=typo ./install-minecraft-splitscreen.sh` (or `curl … | bash` on a Wi-Fi that drops at 30%) on a Deck with a working v1.2 install → the launcher is removed and/or `orchestrator.sh` is truncated, the installer prints "Failed to install the splitscreen launcher — aborting", and the Steam shortcut now fails to start with no pointer to the cause.

Both writers now stage under `$TARGET_DIR` (same filesystem, so each `mv -f` is an atomic rename) and touch the live tree only after validation — the launcher after the `-s`/shebang check, the modules only once every one of them landed. Every early `return 1` removes its staging dir, so a failed run leaves no `.modules.*` litter. The three-tier source fallback, the manifest-is-fatal rule (#49), the stamp step and the return contracts are unchanged; a pre-existing module that is no longer in the manifest is still left in place (as before). Note `mktemp` creates the staged launcher 0600, so after `chmod +x` it is 0700 rather than the previous umask-derived 0755 — the launcher is only ever run by the installing user (Steam launches it as that user), so this is harmless; use `chmod 755` if a shared-machine layout ever matters.

Verification done: (a) `bash -n`; (b) `git apply --check` from the repo root; (c) `tests/test_installer.sh` 17/17 on a scratch clone with the patched file (T7.7, the module-deploy test, still passes through the staging path); the fixture test below is green on the patch and red on the original.

## Tests
Add `test_t7_22` to `tests/test_installer.sh`: create `$TARGET_DIR/minecraftSplitscreen.sh` (`#!/bin/bash\necho WORKING`) and `$TARGET_DIR/modules/orchestrator.sh`; (a) with `SCRIPT_DIR=/nonexistent` and `fetch_url() { : > "$2"; return 22; }` call `setup_splitscreen_launcher_script` (expect return 1) and assert the working launcher still contains `WORKING`; (b) with a two-line manifest and `fetch_url() { printf '#!/bin/bash\n# TRUNC' > "$2"; return 18; }` call `install_runtime_modules` (expect return 1) and assert `orchestrator.sh` is unchanged and `watchdog.sh` does not exist; (c) assert no `.modules.*`/`.minecraftSplitscreen.sh.*` entries remain under `$TARGET_DIR`.

Mutation (PRINCIPLES #4): change `staged`/`stage_dir` back to the live paths — (a) and (b) go red; drop one `rm -rf "$stage_dir"` — (c) goes red. Confirmed in this session.
