title: [C2] download_and_install_jdk exports the highest JDK present, not the one just extracted, and skips version validation
severity: high
security: no
type: Bug
related: #41, #48

## Summary
After extracting a Temurin tarball into the SHARED `$TARGET_DIR/java`, `download_and_install_jdk` locates "the extracted directory" with `find … | sort -V | tail -1` (`modules/java_management.sh:245`) — i.e. the highest-versioned directory present, not the one it just unpacked — and exports it as `JAVA_<major>_HOME` (`:255-256`). `find_java_installation` returns that path first without probing it (`:276-281`), and the post-install branch of `detect_and_install_java` (`:411-421`) prints "Java N automatically installed and configured!" without the `_java_output_matches_major` check that the pre-install branch performs (`:370-392`). A jdk-25 left by an earlier MC 26.x install therefore becomes `JAVA_17_HOME` for a 1.20.4 install, is baked into `polymc.cfg`/`instance.cfg`, and the installer reports success.

## Evidence
```bash
# java_management.sh:244-256
jdk_dir=$(find "$install_dir" -maxdepth 1 -mindepth 1 -type d | sort -V | tail -1)
...
export "${java_home_var}=${jdk_dir}"      # JAVA_17_HOME=.../jdk-25.0.1+9
```
Reproduced with a fixture (pre-planted `jdk-25.0.1+9/bin/java`, tarball containing `jdk-17.0.12+7/`; `fetch_url`/`curl` stubbed):
```
== ORIGINAL
[FAIL] T7.21a got: JAVA_17_HOME=/tmp/…/PolyMC/java/jdk-25.0.1+9
[FAIL] T7.21b returned 0     (a "jdk-17" tarball whose java reports 25 is accepted)
== PATCHED
[PASS] T7.21a exports the JDK just extracted (not the pre-existing jdk-25)
[PASS] T7.21b refuses an extracted JDK of the wrong major
```

## Failure scenario
User installed for MC 26.x earlier (jdk-25 under `$TARGET_DIR/java`), re-runs the installer choosing MC 1.20.4 (Java 17), or takes the custom-mod "switch version" path (`mod_management.sh:1894 detect_java`). jdk-17 downloads and extracts correctly, `JAVA_17_HOME` is exported as the jdk-25 dir, all four instances get Java 25 for a game that expects 17, and the only symptom is a JVM/Fabric crash on first launch of a 4-up game.

The directory name comes from the archive's first entry (`awk 'NR==1'` rather than `head -1` so a multi-thousand-entry listing cannot SIGPIPE `tar` under `pipefail`; a leading `./` is tolerated). The major is verified twice: on the freshly extracted binary (so the export is never wrong) and on the post-install `JAVA_PATH` (so the success message is never wrong, mirroring the pre-install branch). The `exit 1` in the post-install branch matches the existing contract of `detect_and_install_java` ("exits 1 on unrecoverable failure"). Deliberately not changed: the shared install dir layout, the `find_java_installation` search order, and the raw `curl -fL --progress-bar` download at `:211` (a bulk artifact; see C4).

Verification done: (a) `bash -n`; (b) `git apply --check` from the repo root; (c) `tests/test_installer.sh` 17/17 on a scratch clone with the patched file; the fixture test below is green on the patch and red on the original.

## Tests
Add `test_t7_21` to `tests/test_installer.sh`: build a tarball containing `jdk-17.0.12+7/bin/java` (a stub that prints `openjdk version "17.0.12"`), pre-plant `$TARGET_DIR/java/jdk-25.0.1+9/bin/java` (prints 25), stub `fetch_url` to emit a one-entry Adoptium response whose `checksum` is the tarball's sha256, stub `curl` to copy the tarball to its `-o` target, call `download_and_install_jdk 17`, and assert `JAVA_17_HOME == $TARGET_DIR/java/jdk-17.0.12+7` (T7.21a). Second case: a tarball whose `jdk-17…/bin/java` reports 25 must make the function return 1 (T7.21b).

Mutation (PRINCIPLES #4): restore the `find | sort -V | tail -1` line → T7.21a red (exports jdk-25); drop the `_java_output_matches_major` check → T7.21b red. Both confirmed in this session.
