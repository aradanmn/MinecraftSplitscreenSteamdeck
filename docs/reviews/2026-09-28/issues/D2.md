## Summary
`_check_devices_changed` (`modules/controller_monitor.sh:823-833`) implements a 500 ms add-debounce keyed on `_CONTROLLER_MONITOR_DEBOUNCE_MAP`, but since the N16/H1 fix both monitor loops call it as `prev_nodes=$(_check_devices_changed "$mode" "$prev_nodes")` (`:963`, `:973`). Every write to the map (`:833`, `unset` at `:858`) therefore happens in a command-substitution subshell and is discarded: in the parent the map is always empty, `last_ms` is always `0`, and the window never engages. The constant `CONTROLLER_MONITOR_DEBOUNCE_MS` (`:91`), its header entries (`:34`, `:44`, `:62`) and the stderr message all describe behaviour that does not exist. Worse, the logic is wrong even in-process: a debounced add does `continue` but the node is still in `current_nodes`, so `:864` returns it as part of the new baseline and the pad is never re-diffed — a fast remove→add (the exact shape #38's RESUME must see) would silently never spawn/resume until the pad is unplugged again.

## Evidence
`modules/controller_monitor.sh:823-833`:
```bash
        if (( found == 0 )); then
            # Check debounce
            local now_ms
            now_ms=$(_get_epoch_ms)
            local last_ms="${_CONTROLLER_MONITOR_DEBOUNCE_MAP["$ev"]:-0}"
            if (( now_ms - last_ms <= CONTROLLER_MONITOR_DEBOUNCE_MS )); then
                echo "[controller_monitor] Debounced add event for $ev (${CONTROLLER_MONITOR_DEBOUNCE_MS}ms window)" >&2
                continue
            fi
            _CONTROLLER_MONITOR_DEBOUNCE_MAP["$ev"]=$now_ms
```
`modules/controller_monitor.sh:963` (and `:973`):
```bash
                prev_nodes=$(_check_devices_changed "$mode" "$prev_nodes")
```
Reproduction (review probe): after `prev=$(_check_devices_changed docked "")` against a 3-pad fixture, `declare -p _CONTROLLER_MONITOR_DEBOUNCE_MAP` in the parent prints an empty map; after one in-process call it holds 3 entries. The new test T2.23 below reproduces the in-process swallow: second ADD inside 500 ms is missing (`second ADD (re-add inside 500 ms): got ''`) on the current code.

## Failure scenario
Today: harmless but misleading — no debounce at all, while the constant, docstring, header and the "Debounced add event" message claim one. If anyone "fixes" the subshell loss in isolation (e.g. a nameref out-param): a pad that flaps remove→add inside 500 ms (Bluetooth re-key, a loose USB-C hub, the fast reconnect #38 was built for) gets its re-ADD swallowed, enters the baseline as "known", and never spawns / never RESUMEs until it is physically unplugged and replugged.

## Suggested fix
Delete the debounce. The orchestrator serialises every message (PRINCIPLES #10) and a duplicate ADD for an active, connected pad is already a no-op (`slot_claim` → `REJECT`, `modules/slot_manager.sh:218-219`); a remove→add pair inside the window is a legitimate reconnect that must be delivered. The Deck has been validated (2026-06-26 4-DS4, 2026-07-25 reconnect) with the debounce effectively off, so this changes no shipped behaviour — it only removes a latent one.
