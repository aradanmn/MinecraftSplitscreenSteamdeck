## Summary
`_start_nested_plasma` writes `~/.config/autostart/splitscreen-prod.desktop` whose `Exec=env … minecraftSplitscreen.sh prodFromPlasma` (`minecraftSplitscreen.sh:286-292`). The ONLY `rm -f` of that file is inside `launchProdFromPlasma` (`:554`) — it is removed only if the autostart actually ran. `launchFromPlasma`'s boot phase explicitly tolerates the inner handler being ABSENT (`:514`) and proceeds to teardown without removing the file. `runtime_context.sh:362-363` warns about precisely this ("a missed rm here strands an autostart that relaunches the game on every Plasma login"). The `prodFromPlasma)` dispatch arm (`:1043-1052`) then runs `launchProdFromPlasma` unconditionally — unlike `*)` (`:1185`) and `launchFromPlasma` (`:402`) it never checks `MCSS_NESTED_SESSION`/gamescope context — so the next real Desktop-Mode login runs the production handler on the user's real desktop.

## Evidence
```bash
# minecraftSplitscreen.sh:508-514 — boot phase ends with the handler ABSENT, file untouched
while (( _boot < _boot_budget_s )) && [[ -z "$(_mcss_own_run_pids 'prodFromPlasma')" ]] …; do sleep 1; …; done
echo "[launchFromPlasma] nested session boot phase ended after ${_boot}s (inner handler $( … && echo up || echo ABSENT ))" >> "$LOG"
# minecraftSplitscreen.sh:1043-1048 — no guard
prodFromPlasma)
    echo "[main] Production launch — prodFromPlasma (inside nested Plasma)" >> "$LOG"
    if declare -f launchProdFromPlasma >/dev/null 2>&1; then
        launchProdFromPlasma
# minecraftSplitscreen.sh:557-558 — what then runs on the real desktop
pkill -x plasmashell 2>/dev/null || true
( while :; do pkill -x plasmashell 2>/dev/null; sleep 2; done ) &
```
Confirmed code path; the trigger (nested Plasma never running its autostart — crash, session-start failure, the 90 s boot budget) is plausible and has been observed as "inner handler ABSENT" in logs.

## Failure scenario
Nested Plasma fails to run the autostart → file stranded → the user switches to Desktop Mode → Plasma runs the autostart with `MCSS_NESTED_SESSION=plasma` (on the Exec line) → `launchProdFromPlasma` on the real desktop: `pkill -x plasmashell` every 2 s (panel and desktop gone, A7), the real orchestrator spawns instances on the desktop, and on exit `qdbus org.kde.Shutdown … logout` logs the user out. The #42-class regression path, reachable without any user mistake.

## Suggested fix
(1) Remove the prod autostart file unconditionally once the boot phase ends (no-op when the inner handler already did). (2) Gate the `prodFromPlasma)` arm on a sourceable predicate `_mcss_prod_entry_allowed` — nested session (`MCSS_NESTED_SESSION != 0`) AND gamescope origin (`MCSS_ENV_CONTEXT == gamescope`; both ride the autostart Exec line via `mcss_exec_env_string`, and `mcss_resolve_environment` keeps a carried value) — and on refusal remove the stranded file, notify, exit 1.

Why this is correct: the autostart entry is consumed by Plasma at session start only, so deleting it after the boot phase can never lose a legitimate run; `MCSS_ENV_CONTEXT=gamescope` cannot be present on a real Desktop-Mode login (the real Plasma sets `XDG_CURRENT_DESKTOP=KDE` and no Exec line carries it), which is precisely the distinguishing signal. It deliberately does NOT change the test autostart (`splitscreen-test.desktop`, removed by `launchTestFromPlasma`) or the `*)` guard; A7 makes the plasmashell kill safe independently.

Checks done: (a) `bash -n` — OK; (b) `git apply --check` against the pristine tree — OK; (c) `tests/test_orchestrator.sh` (sources the launcher) on the patched tree — 9/9; the three new tests below are red on the original and green on the patched file.

## Tests
Add to `tests/test_orchestrator.sh` (or a new `tests/test_launcher_entry.sh`): T-A5a runs `launchFromPlasma` with `_start_nested_plasma` stubbed to write the autostart file and never start an inner handler, and asserts the file is gone afterwards (mutation: drop the new `rm -f` → red). T-A5b asserts `_mcss_prod_entry_allowed` returns 1/1/0 for bare / nested-but-desktop / nested-gamescope (mutation: `return 0` unconditionally → red).
