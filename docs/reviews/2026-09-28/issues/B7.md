## Summary
`modules/instance_creation.sh:401-443` resolves download URLs for dependencies with four near-identical inline `jq` filters that duplicate `match_modrinth_version` (`modules/mod_management.sh:221`, the #88 canonical ladder that ARCHITECTURE §2 says lives there once), then adds a fifth tier the canonical ladder deliberately does not have: the first Fabric file for ANY Minecraft version, with none of `_version_fallback_allowed`'s gating. `fetch_and_add_external_mod` (`modules/mod_management.sh:1096-1109`, C10) feeds exactly this path: it appends every transitive Modrinth dependency with `MOD_URLS+=("")` "to be resolved during download", so a dependency with no build for `MC_VERSION` is not skipped — a build for some other version is installed and copied to all four instances.

## Evidence
`modules/instance_creation.sh:439-443`:
```bash
# If still no URL found, try the latest Fabric version for any compatible release
if [[ -z "$mod_url" || "$mod_url" == "null" ]]; then
    print_debug "Trying latest Fabric version (any compatible release)"
    mod_url=$(printf "%s" "$resolve_data" | jq -r '.[] | select(.loaders[] == "fabric") | (.files | map(select(.primary)) | .[0].url) // (.files[0].url)' 2>/dev/null | head -n1)
```
`modules/mod_management.sh:1102`: `MOD_URLS+=("")  # Empty URL - will be resolved during download`. Reproduced with T8.2 below against the pristine module: a dependency whose only Fabric build lists `1.20.1` is installed for `MC_VERSION=1.21.4` (`wrong-version jars=1`).

## Failure scenario
A custom mod requires library X whose newest build is for 1.21.1 while the selected version is 1.21.5 -> `X-1.21.1.jar` installed into instance 1 and copied to 2-4 -> Fabric loader refuses to start ("incompatible mod set") on every instance, with nothing in the installer summary pointing at X.

## Suggested fix
Replace the private ladder with one call to `match_modrinth_version "$resolve_data" "$MC_VERSION" 1` (same `check_standalone=1` guard the compatibility scan used to accept the parent mod) and drop the any-version tier; no match -> the existing "could not be downloaded" path records it in `MISSING_MODS`.

Mutation: pristine module -> T8.2 red (`wrong-version jars=1`), observed. `match_modrinth_version` is defined in `mod_management.sh`, which the installer entry sources before `instance_creation.sh` runs (same unguarded cross-module use as the existing `get_curseforge_download_url` call at `:456`).

Why correct: the canonical ladder is a superset of tiers 1-3 (exact, major.minor, .x) plus `.0`, and it only omits the "previous patch" tier and the any-version tier — both of which can select a jar built for a different game version, which is what this issue is. Deliberately NOT changed: the CurseForge dependency path (`get_curseforge_download_url`, its own preserved ladder per the #88 notes), the debug-dump block, and `fetch_and_add_external_mod`.

**Fuller fix (C10):** resolve at ADD time instead of download time — in `fetch_and_add_external_mod`'s Modrinth branch fetch `/project/<id>/version` and run `match_modrinth_version`, storing the URL (and, with B8, the hash) or skipping the dependency with a visible warning during selection, so an incompatible transitive dependency is reported before any download starts. The C16/C19 ladder copies in the same family should be retired in the same pass (see the consolidated review "Copies of the version-match ladder").

    local versions_json="$1" jar_body="$2" out="$3"
    (
        MC_VERSION="1.21.4"; FABRIC_VERSION="0.16.9"; LWJGL_VERSION="3.3.3"

}
