title: [C6] detect_and_install_java sources the user's ~/.profile into the installer (dies under set -u, runs arbitrary shell)
severity: medium
security: yes
type: Bug
related: #41
---
## Summary
`modules/java_management.sh:366` and `:408` run `[[ -f ~/.profile ]] && source ~/.profile 2>/dev/null || true` inside the installer's `set -euo pipefail` process. The `|| true` protects against a failing *command*, not against an *expansion error*: under `set -u` an unbound-variable reference anywhere in the user's `.profile` is a shell error that exits the non-interactive shell — and because stderr is `2>/dev/null`, the installer dies with no message at all (exit 127 in this session's bash 5.2). The line is vestigial: #41 removed the `~/.profile` edits, `download_and_install_jdk` exports `JAVA_<ver>_HOME` in-process (`:252-256`), and `find_java_installation` scans the install dirs directly, so nothing is gained. It also executes whatever the profile contains (`exec`, `PATH`/`IFS` changes, interactive-only commands) inside the installer.

## Evidence
```bash
# java_management.sh:365-366 (and again at :407-408 after the JDK install)
# Source the profile to get any existing Java environment variables
[[ -f ~/.profile ]] && source ~/.profile 2>/dev/null || true
```
Reproduction (fake `HOME` whose `.profile` is `export FOO="$UNSET_THING"`; `get_required_java_version`/`find_java_installation` stubbed so no network is needed):
```
== ORIGINAL
🔄 Searching for Java 21 installation...
rc=127            <- no error text at all; "SURVIVED" never prints
== PATCHED
[PASS] detect_and_install_java survives an unbound-variable ~/.profile
```

## Failure scenario
A Deck user whose `~/.profile` references `$SSH_AGENT_PID`, `$XDG_RUNTIME_DIR`-derived paths, or any variable set only by their login session → the installer stops right after "Searching for Java … installation..." with a blank line and a non-zero exit. Nothing points at `.profile`.

Pure deletion. A user who set `JAVA_21_HOME` in `.profile` for their own reasons still gets it honoured when they run the installer from a login shell (it is already in the environment); the installer just no longer re-reads the file itself. No other behaviour changes.

Verification done: (a) `bash -n`; (b) `git apply --check` from the repo root; (c) `tests/test_installer.sh` 17/17 on a scratch clone with the patched file; the behavioural test below is green on the patch and red (silent exit) on the original.

Mutation (PRINCIPLES #4): re-add either `source ~/.profile` line → the test goes red (exit 127, no output). Confirmed in this session.
