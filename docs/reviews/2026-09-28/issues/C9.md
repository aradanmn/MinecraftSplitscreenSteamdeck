title: [C9] Version scan re-fetches every required mod's full version list per candidate (140 calls) and treats API errors as "incompatible"
severity: medium
security: no
type: Bug
related: #88

## Summary
`get_supported_minecraft_versions` (`modules/version_management.sh:98-125`) calls `check_mod_version_compatibility` for each of up to 20 candidate versions × every required mod, and that function (`:189-207`) fetches `${MODRINTH_API_BASE}/project/$mod_id/version` — the same URL, the same multi-hundred-entry body — on every call: 20 × 7 = 140 downloads for the default `mods.conf`. Any non-200 or transport failure (`:205-207`) returns 1, which the caller records as "Missing required mod support" and silently removes the version from the menu. A brief Modrinth 429 (documented limit 300 req/min, which 140 rapid calls approach) or 5xx therefore makes versions disappear with a misleading reason, and a persistent failure ends in the generic "No Minecraft versions found … may be due to API issues". The custom-mod version-switch path runs the whole scan twice back-to-back (`mod_management.sh:1872` then `:1888`).

## Evidence
```bash
# version_management.sh:121 — per version, per mod …
if ! check_mod_version_compatibility "${REQUIRED_SPLITSCREEN_IDS[$i]}" … "$mc_version"; then
# … and :198-207 — a fresh download of the same body each time; any failure == "incompatible"
http_code=$(fetch_url_status "$api_url" "$tmp_body")
if [[ "$http_code" != "200" ]] || ! … jq -e . …; then
    return 1
fi
```
Fixture run (3-release Mojang manifest, one required Modrinth mod, `fetch_url_status` counting its calls / returning 429):
```
== ORIGINAL
[FAIL] T7.24a fetches=3 out=[1.21.1]                        (one fetch per candidate)
[FAIL] T7.24b: ❌ 1.21.3 - Missing required mod support: Sodium  (a 429 reported as incompatible, x3)
== PATCHED
[PASS] T7.24a one fetch per required mod (got 1), result 1.21.1
[PASS] T7.24b 429 is reported as could-not-verify, not incompatible
```

## Failure scenario
"Testing 1.21.5…" hits a 429 on Sodium's list → 1.21.5 is not offered and the line says "Missing required mod support: Sodium", which is false; the user picks 1.21.4 for no reason. Under a longer outage every version is dropped and the message blames "API issues" without naming the mod or the HTTP status.

## Suggested fix
Minimal safe diff: fetch each required mod's list ONCE per scan (in-memory cache keyed by platform:id), retry once with a short backoff, and make "could not fetch" a distinct return code (2) that the scan reports by name — the version is still not offered, but the reason is now true and actionable.

The cache is an associative array in the same process as the scan (the scan runs inside `$(get_supported_minecraft_versions)`, so it lives exactly one scan — the second scan on the version-switch path still costs one fetch per mod, not one per version); no temp files outlive a call. The CurseForge branch keeps the existing raw `curl` shape but adds `--max-time 15` so the scan cannot hang there (C4 converts it to `fetch_url_status` with a header file — land C4 first or convert this line in the same PR). The ladder logic, `strict_mode`, and the "version not offered" outcome for a genuine mismatch are untouched. `rc=2` propagates through the strict path for the extra custom mod too, but that caller only tests non-zero, so it keeps its current behaviour.

Fuller fix (design decision, PRINCIPLES #5 fail-open): on `rc=2` keep the version in the list, tagged "(unverified: Sodium)", and let `check_mod_compatibility` — which already prints the API-error warning and continues — make the final call at install time. That is the fail-open behaviour the review asks for; it is left out of the minimal diff because offering an unverifiable version changes what `--yes` installs unattended, which should be decided explicitly. The same "API error == not compatible" fail-closed shape also lives in `check_modrinth_mod`/`check_curseforge_mod` (`mod_management.sh:380-389`, `:481-488`) and can reuse `_mod_versions_cached` once it moves to `mod_management.sh` (the policy owner per ARCHITECTURE §2).
