## Summary
`get_fabric_version` (`modules/version_management.sh:404-405`) and `download_prism_launcher` (`modules/launcher_setup.sh:73-84`) capture a `fetch_url … | jq` pipeline with a plain assignment. In `-` (stdout) mode `fetch_url` has no `-f`, so an HTTP error still returns 0, but a DNS/connect/`--max-time` failure returns curl's non-zero status; `pipefail` carries it through `jq`/`head`, the assignment fails, and because `main_workflow.sh:94-104` calls both functions as plain statements, `errexit` kills the installer with only curl's one-line stderr. The documented `FABRIC_VERSION="0.16.9"` fallback and the "Could not find latest PolyMC AppImage URL" error are dead on exactly the failure they exist for. The two sibling sites in `modules/java_management.sh:114,135` (`get_required_java_version`) and `modules/version_management.sh:84-87` (`get_supported_minecraft_versions`) have the same shape but are protected today only by an accident: both run inside `$(...)`, and bash does not inherit `errexit` into command substitutions unless `shopt -s inherit_errexit` is set (it is not). They are latent, not live — one `shopt` or one direct call away from the same abort.

## Evidence
```bash
# version_management.sh:404-405 — a plain assignment from a failing pipeline
FABRIC_VERSION=$(fetch_url "${FABRIC_META_BASE}/versions/loader" - \
    | jq -r '.[0].version' 2>/dev/null)
# Fallback to known stable version if API call fails   <- never reached on curl rc 6/7/28

# launcher_setup.sh:73-84 — same shape; print_error at :88 never fires
prism_url=$(fetch_url "https://api.github.com/repos/PolyMC/PolyMC/releases/latest" - | \
    jq -r '...' | head -n1)
```
Reproduction (scratch harness, `fetch_url() { return 6; }`, functions called as plain statements under `set -euo pipefail`, bash 5.2.21):
```
[FAIL] get_fabric_version reaches the 0.16.9 fallback (rc=6)  -- process died, no message
[FAIL] download_prism_launcher (rc=6)                          -- ditto
[FAIL] get_required_java_version … (only with shopt -s inherit_errexit; passes without it)
```
With the patch below all four sites reach their fallback/error path.

## Failure scenario
A Wi-Fi drop or a 15 s stall on `meta.fabricmc.net` after the user has picked a version: the installer exits with `curl: (6) Could not resolve host` and nothing else — no `print_error`, no fallback, no instances created. Same for `api.github.com` at the very first network step (`download_prism_launcher`).

`|| var=""` is the smallest errexit-safe form: the assignment's failure is now the left side of `||`, so `set -e` ignores it and the existing `-z` checks take over. The `2>/dev/null` added to the Fabric site keeps the bare `curl: (6)` line off the terminal now that the function prints its own warning. The `java_management.sh` sites are latent (see Summary); the guard is still correct and cheap. Nothing else changes: no new helper, no timeout change, no behaviour change on success.

Fuller fix: a `fetch_url_body_or_empty url` helper in `utilities.sh` (always returns 0, echoes body or empty) would make every `$(fetch_url … -)` site safe by construction (PRINCIPLES #9) — there are ~10 of them across the installer; do that as a follow-up once this landing is validated.

Verification done: (a) `bash -n` on all three patched files; (b) `git apply --check` from the repo root against the pristine tree; (c) `tests/test_installer.sh` 17/17 on a scratch clone with the patched files; the new T7.19 harness below is green on the patched copy and red (3 of 4 cases) on the original.
