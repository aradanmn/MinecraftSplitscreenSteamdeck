## Summary

`compute_grid_mode` (`modules/window_manager.sh:208-236`) was deliberately changed to be COUNT-based ("Was highest-slot-based, which left {2,4} as 'quad' and a lone slot-4 in a corner", deployed 2026-06-23 per `docs/TODO.md:321`). `tests/test_window_manager.sh:38-48` (T3.1 cases `"2:half"`, `"1 3:quad"`, `"3:quad"`, `"4:quad"`, `"2 4:quad"`) and `:216-231` (T3.9 `compute_grid_mode "3"` → `quad`) still encode the OLD contract, so 6 sub-cases fail *because the code is correct*, and `.github/workflows/ci.yml:74` sets the baseline to 7 to tolerate it. The consequence is inverted: reintroducing the highest-slot bug makes the suite 9/9, CI prints `OK: 9 >= 7`, and nothing notices. The intended behaviours ({2}→full, {2,4}→half, {1,3}→half, {3}→full) have zero unit coverage.

## Evidence

Pristine suite on the current (correct) code:

```
[FAIL] T3.1.3 — slots='2': expected 'half', got 'full'
[FAIL] T3.1.4 — slots='1 3': expected 'quad', got 'half'

```

Pristine suite against a scratch clone whose `compute_grid_mode` was mutated back to highest-slot (`highest=$slot` / `highest<=1 full, ==2 half, else quad`):

```
9/9 tests passed.
```

That is the PRINCIPLES #4 anti-pattern with the extra twist of being red-on-correct-code.

## Failure scenario

A PR mangles or reverts `compute_grid_mode` to slot-number-based → suite improves from 7/9 to 9/9 → CI passes → a lone P4 sits in a quarter of the TV again and {2,4} plays in two corners.

## Suggested fix

Rewrite the T3.1 table to the documented count contract; rewrite T3.9 to assert the scale-down rule through the same order-mapping `apply_layout` uses (`window_manager.sh:323-343`: half/full cells by ORDER among active slots, quad cells by slot number); bump the CI baseline to 9. `TEST_TOTAL` stays 9.

Note on the `ci.yml` hunk: the F2 CI-gate issue also edits the `BASELINE` map; apply whichever lands second by hand (one-line conflict). With the baseline left at 7 the suite would still pass CI, but the inverted-test hazard would only be *reduced* (a revert would still print 7 ≥ 7); 9 is what makes the gate bite.

## Tests

The diff IS the test change. Mutation (PRINCIPLES #4), done above: re-invert `count` → highest-slot in `compute_grid_mode` → 7/9, exit 1. A second useful mutation: in `apply_layout` swap `if quad then cell=$slot else cell=$order` → T3.9 does not see it (it calls the pure functions, not `apply_layout`); covering that needs `apply_layout` driven through a stubbed `_position_slot` (fuller fix, not in this diff).

## Hardware verification

Game Mode docked, TV, 4 pads (stage3_hotplug covers the join half; this covers the leave half). Start 4 players, then quit P2 and P4 (active {1,3}): expect P1 in the TOP half and P3 in the BOTTOM half of the TV, not two corners. Quit P1 (active {3}): expect P3 fullscreen. Proof: `grep '\[window_manager\]' /tmp/splitscreen-debug-latest.log | tail` shows `grid=half` after the first leave and `grid=full` after the second (and `hw_expected_slot_geometry` from review T9, once fixed, can assert it in a stage5-style check). Also confirm the join order is untouched: P1..P4 joining still lands in UL/UR/LL/LR (stage3 D3.4-D3.6).
