## Summary

`tests/test_module_resource.sh:33-48` hand-copies the installer module list ("11 of them" in the comment, 10 in the array): `version_stamp.sh` (#89) was never added, so its re-source safety — the HW-1 double-source abort this suite exists to catch — is unverified. Source of truth is `install-minecraft-splitscreen.sh:129-139` (`INSTALLER_MODULE_FILES`, 11 entries), which `tests/test_installer.sh` T7.2 already parses. While mutation-testing the fix, a second defect surfaced: the suite's `2>&1` sits *outside* the command substitution (`:75-87`), so the subshell's stderr never reaches `$out`, and bash does not abort on a `readonly` re-declaration inside a sourced file even under `set -e` — it prints `readonly variable` and continues. With stderr captured, `modules/controller_proxy.sh:121-132` fails today: its five top-level `readonly CONTROLLER_PROXY_*` lines lack the `_*_CONSTANTS_LOCKED` guard every other module uses.

## Evidence

```bash
# tests/test_module_resource.sh:33-48 — 10 entries, comment says 11
INSTALLER_MODULES=(
    utilities.sh
    java_management.sh
    ...
    main_workflow.sh

# tests/test_module_resource.sh:75-83 — stderr of the subshell escapes the capture
    out=$(
        set -euo pipefail
        source "$path"
        source "$path"

```

Mutation runs in a scratch clone (bash 5.2.21):


## Failure scenario

A stage script (or `run_all.sh`, which sources every stage into one shell) sources `controller_proxy.sh` twice → five `readonly variable` lines on stderr per re-source; a future module that *does* abort (a `readonly` array, a `declare -r` in POSIX mode, `set -e` at a top-level failing command) reproduces HW-1 while this suite stays 22/22. A `readonly` added to `version_stamp.sh` — sourced by both `deploy.sh` and the installer — is never exercised at all.

## Suggested fix

Parse the list from the installer (the T7.2 grep), move the `2>&1` inside the substitution, and guard `controller_proxy.sh`'s constants block with the house `_CONTROLLER_PROXY_CONSTANTS_LOCKED` pattern (`runtime_context.sh:148`, `dock_detection.sh:46-54`) so the fixed suite is green on the current tree.

Why the guard is safe: the sentinel is process-local and not exported (same as the other modules), so a fresh process still gets the constants; the unit suites that pre-set `_*_CONSTANTS_LOCKED=1` to override timeouts (`test_orchestrator.sh:105`) get the same escape hatch for the proxy constants. Deliberately NOT changed: `test_installer.sh` T7.2's own count (review T21), or the suite's `TEST_TOTAL` derivation (it is computed from the two lists, so it moves to 23 by itself; `test_module_resource.sh` is not in the CI `BASELINE` map — review T6/F2).

## Tests

The suite is the test; its `TEST_TOTAL` is derived, so a new installer module is covered without editing it. Mutations (PRINCIPLES #4), run in the scratch clone against the patched suite:

```
readonly _VS_PROBE="$RANDOM" appended to version_stamp.sh:
[FAIL] version_stamp.sh — double-source produced unexpected output: ... line 157: _VS_PROBE_T10: readonly variable
dock_detection.sh guard removed:
[FAIL] dock_detection.sh — double-source produced unexpected output: ... line 51: DOCK_DETECTION_DEFAULT_DRM_PATH: readonly variable
```

(both 21/23 before the controller_proxy guard, 22/23 after). Removing `version_stamp.sh` from the installer's array would drop it from the suite too — that is the intended single-owner behaviour; `test_installer.sh` T7.3-style membership asserts remain the place to pin required entries.
