## Summary
The file's own "Session-env leak guard" (`minecraftSplitscreen.sh:145-198`) documents that the nested `startplasma-wayland` pushes its environment into the shared `systemd --user` manager (`dbus-update-activation-environment --systemd`, `--all`). Everything the launcher exported goes with it: `SPLITSCREEN_DEBUG_LOG` (the #58/#60 process marker), every `MCSS_*` export, `SPLITSCREEN_FIFO/STATE`, and the shim-prepended `PATH` (`:277`). `_restore_session_env` restores only `WAYLAND_DISPLAY`/`DISPLAY` (`:187-198`). Services the REAL Desktop-Mode session later starts through the manager (Plasma's systemd boot: `plasma-kwin_wayland`, `plasma-plasmashell`, baloo, kded…) then carry `SPLITSCREEN_DEBUG_LOG=` in `/proc/PID/environ`, so `_mcss_nested_pids` (any marker value) matches the real desktop — the case the #58 scoping was added to exclude ("a dying desktop is left alone"). Status: PLAUSIBLE — confirm on the Deck (step 1 below) before merging.

## Evidence
```bash
# minecraftSplitscreen.sh:168 — only two vars are snapshotted/restored

# minecraftSplitscreen.sh:277 — exported PATH with the helper dir in front

# minecraftSplitscreen.sh:450-453 — STARTUP GUARD kills any MARKED kwin/plasma_session/baloo

    for _pid in $(_mcss_nested_pids "$_name"); do kill -9 "$_pid" …
```
The test below shows the original `_restore_session_env` issues only two `set-environment` calls against a manager that reports `SPLITSCREEN_DEBUG_LOG`, `MCSS_MODE`, `MCSS_HELPER_DIR`, `SPLITSCREEN_FIFO` and a shim-prefixed `PATH`.

## Failure scenario
Desktop → Game Mode with the outgoing desktop still tearing down (the exact #58 scenario), on a Deck that has run one nested session since boot: the STARTUP GUARD's `kill -9` over `_mcss_nested_pids 'kwin_wayland' / 'plasma_session' / 'baloo_file'` hits the real session's processes. Secondary: every later user service runs with `/run/user/1000/mcss` first in PATH and a stale `MCSS_MODE`/`SPLITSCREEN_FIFO` in its environment.

## Suggested fix
Snapshot `PATH` too (before the prepend), restore it to the snapshotted value (never unset it), and scrub every `SPLITSCREEN_*`/`MCSS_*` name from the manager on restore — before the snapshot-file guard so both the inner trap and the outer supervisor run it (idempotent).

Why this is correct: `unset-environment` only affects services spawned AFTER the call; every process of the nested session already has its environ, so run-scoped kills (`_mcss_own_run_pids`) keep working through teardown, and helpers systemd respawns afterwards are exactly the class the `plasma-workspace.target` stop handles (documented at `:631-636`). Restoring PATH to the pre-nesting manager value is what the existing guard does for the two display vars. It deliberately does NOT touch non-launcher variables (asserted by the test) and does NOT change the marker mechanism (A8 fixes its coverage; A8 + A9 together make the marker mean "our run" again).
