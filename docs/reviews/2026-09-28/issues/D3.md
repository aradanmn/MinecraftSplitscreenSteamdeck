## Summary
The #38 fix for the 2026-07-25 on-Deck "MCSS-virtual pollution" failure added the `MCSS-slot*` name gate only inside `_consider` of the raw enumerator (`modules/controller_monitor.sh:551`). The two other enumeration sources have no such gate: `_map_external_player_virtuals` (`:341-350`, selected by the documented, supported escape hatch `CONTROLLER_MONITOR_RAW_BINDING=0`) classifies every non-`28de` js device as an external, and the handheld branch of `list_eligible_controllers` (`:689`) takes "the first gamepad-capable device (any VID:PID)" from `_parse_all_gamepad_devices` (`:246-276`). Our evsieve virtuals advertise the physical pad's real VID:PID (`device-id=054c:09cc`, so Controlify shows DS4 glyphs), so they pass every other gate. `parse_input_device_blocks` already delivers the `name` field to all three readers; the gate should be one helper applied at the shared reader (PRINCIPLES #9).

## Evidence
`modules/controller_monitor.sh:550-554` — the only gate:
```bash
        local _nm="${name#\"}"; _nm="${_nm%\"}"
        if [[ "$_nm" == MCSS-slot* ]]; then
            echo "[controller_monitor]   raw: drop event${_eventN} js${_jsN} [${vendor}:${product}] — MCSS proxy virtual (${_nm})" >&2
            return 0
        fi
```
`modules/controller_monitor.sh:345-350` — legacy mapper, no name gate:
```bash
        if [[ "$vnd" == "$MCSS_STEAM_VENDOR_ID" && "$prd" == "$MCSS_STEAM_PRODUCT_ID" ]]; then
            virtuals+=("$inputn $ev $js")
        else
            externals+=("$inputn $ev $js ${vnd:-0000} ${prd:-0000}")
        fi
```
Reproduction (review probe, `CONTROLLER_MONITOR_RAW_BINDING=0`, 3 DS4 + one `MCSS-slot1` block): `enumeration: 4 external pad(s)` including `external: input30 [054c:09cc] event9 js3` — the proxy virtual. New tests T2.24/T2.25 below reproduce both branches on the current code (`got 2 line(s)` / `got '/dev/input/event40 /dev/input/js0 054c 09cc'`).

## Failure scenario
- Escape hatch (`CONTROLLER_MONITOR_RAW_BINDING=0`) with the default-on proxy: each real pad's evsieve virtual is enumerated as a 5th/6th "external", claims a Steam virtual as a phantom player, and its create/destroy churn misroutes `CONTROLLER_ADD`/`REMOVE` — exactly the 2026-07-25 failure, now living in the documented fallback path.
- Handheld: evsieve is only stopped on `SLOT_DIED`, so an `MCSS-slot<N>` virtual can outlive a docked→handheld transition; `list_eligible_controllers handheld` then returns the proxy virtual as "the" pad (it is often the lowest jsN among survivors) and P1 is bound to a device nobody holds.

## Suggested fix
One helper, `_is_mcss_proxy_virtual NAME`, applied in `_parse_all_gamepad_devices` (which both the handheld branch and `_map_external_player_virtuals` read) and reused by the existing raw gate.

## Hardware verification
Mode: **Game Mode, docked**, 2 DS4s, proxy at default. (1) Escape hatch: add `CONTROLLER_MONITOR_RAW_BINDING=0` to the launch options, launch, connect both pads; `grep 'enumeration:' /tmp/splitscreen-debug-latest.log` must report `2 external pad(s)` after both proxies are up (before the fix it grows to 3-4 as `MCSS-slot*` virtuals appear) and `grep -c 'CONTROLLER_ADD' ` must equal the number of physical pads; unplug/replug P2 → `RESUME slot 2`, not `REJECT`. (2) Handheld leftover: with the default raw binding, launch docked 2-up, then undock (real cable pull) — after the docked→handheld transition, `grep 'Initial controller present\|CONTROLLER_ADD' /tmp/splitscreen-debug-latest.log | tail -3` must name the Deck's own pad (`28de:11ff`), never `event<N>` of an `MCSS-slot*` device (`cat /proc/bus/input/devices | grep -B2 -A4 MCSS-slot` shows which nodes those are). Stage: `tests/hardware/stage3_hotplug.sh` (docked baseline) then a manual undock; the escape-hatch run is a one-off, not a stage.
