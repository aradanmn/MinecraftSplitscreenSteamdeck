## Summary
`EVSIEVE_RELEASE_ASSET_BASE_URL` (`modules/evsieve_management.sh:98-102`) is `https://github.com/aradanmn/MinecraftSplitscreenSteamdeck/releases/latest/download`; `_evsieve_try_prebuilt` (`:213-239`) fetches `.stamp`, `.sha256` and the binary from that one mutable location and compares them **against each other**. The only pinned values are `commit=`/`patch_sha256=` in the stamp, which the same publisher writes. Unlike the source path (pinned `EVSIEVE_SOURCE_ARCHIVE_SHA256`, pinned commit, SHA-verified patch), nothing in the tree pins the *binary's* digest, so "checksum-verified" detects transport corruption only — a swapped `latest` asset with a matching `.sha256` passes every check and a binary that grabs every player's input device is installed. Separately, every other network location derives from `MCSS_REPO_RAW_URL` (`install-minecraft-splitscreen.sh:115`, itself hard-coding `aradanmn`), but this URL is an independent literal: a fork installing from its own `REPO_REF` still executes aradanmn's binary.

## Evidence
`modules/evsieve_management.sh:98-99`:
```bash
    readonly EVSIEVE_RELEASE_ASSET_BASE_URL=\
"https://github.com/aradanmn/MinecraftSplitscreenSteamdeck/releases/latest/download"
```
`modules/evsieve_management.sh:234-238` — remote digest vs remote bytes, no local anchor:
```bash
    expected_sha=$(grep -oE '^[0-9a-f]{64}' "$sha_file")
    [[ -n "$expected_sha" ]] || return 1
    actual_sha=$(sha256sum "$bin_file" 2>/dev/null | cut -d' ' -f1)
    [[ "$actual_sha" == "$expected_sha" ]] || return 1
```
`install-minecraft-splitscreen.sh:115`:
```bash
export MCSS_REPO_RAW_URL="https://raw.githubusercontent.com/aradanmn/MinecraftSplitscreenSteamdeck/${REPO_REF}"
```
Current published asset (fetched 2026-09-28 from `releases/latest` → v1.2.4): `evsieve-x86_64-linux.sha256` = `68dbf3380c0a4f1eef93a4e9b8c099aa1f1f8023a843d5165e6dd871518f5c2a`, stamp `commit=ebd7efe1…` / `patch_sha256=9ec2cd9d…` (matches the module's pins). Reproduction: new test T23 — an asset that matches its own `.sha256` but not any in-tree value installs on the current code (`20/21`, red).

## Failure scenario
A mistaken or malicious re-upload of the `latest` release assets (the release is editable; `latest` is a moving pointer, never a tag), or a fork owner who expects their fork's binary, passes stamp + checksum and is installed with no local pin to catch it. The binary runs as the user with read access to every `/dev/input/event*` and write access to `/dev/uinput` for every session.

## Suggested fix
Minimal safe diff: (1) pin `EVSIEVE_PREBUILT_SHA256` in the module next to the source pins (value = the v1.2.4 asset's digest above), check the published `.sha256` against it *before* downloading the binary (early abort) and the downloaded bytes against it after (the trust anchor); (2) derive the owner/repo from one installer constant `MCSS_REPO_SLUG` that `MCSS_REPO_RAW_URL` is also built from (release.yml passes `github.repository`); (3) make release.yml print the built digest on every run and refuse to publish a **tag** whose build does not match the pin (an unmatched asset is unusable by every install anyway — better to fail the release loudly than ship a silent fall-through to the broken #196 path).

Why this is correct and what it deliberately does NOT change: trust now rests on a value in the tree (reviewed, versioned, signed by the commit), not on the release page; the stamp check stays as the cheap first abort; the pin is a function call (`_evsieve_prebuilt_digest_ok`) so the unit suite stands in for it exactly as it stands in for `fetch_url` — the pin itself is never env-overridable; `MCSS_REPO_SLUG` follows ARCHITECTURE §3 (env-overridable at its canonical home only, bare `${MCSS_REPO_SLUG:?}` in the consumer so a sourcer that forgot it fails loudly rather than fetching from `github.com//releases`). Release procedure after this lands: bump `EVSIEVE_PINNED_COMMIT`/patch → `workflow_dispatch` the release job (it already supports that and uploads an artifact) → copy the printed digest into `EVSIEVE_PREBUILT_SHA256` → commit → tag. **Design decision flagged**: (3) assumes the tag's rebuild is byte-identical to the dispatch build (Rust release builds with a pinned `Cargo.lock` on the same runner image usually are, but `dtolnay/rust-toolchain@stable` floats). If a real tag ever trips the gate, the fuller fix is to stop rebuilding on the tag (publish the dispatch run's artifact) or to sign instead of pin: `ssh-keygen -Y sign` the `.sha256` in CI with a repo secret and verify with `ssh-keygen -Y verify` against a public key in-tree — reproducibility then no longer matters and forks simply carry their own key. Either is a follow-up; the pin is the smallest change that closes the hole today.
