## Summary
The header of `uninstall-minecraft-splitscreen.sh:5` calls it a "Standalone, curl|bash-able uninstaller", but both prompts — `read -r -p "Keep my data? [Y/n]: " keep_choice` (`:183`) and `read -r -p "Are you sure you want to continue? [y/N]: " confirm` (`:235`) — read stdin. When the script itself arrives on stdin, `read` consumes the next not-yet-parsed line of the script (a blank line after the enclosing `if…fi`), so `keep_choice=""` selects keep-data and `confirm=""` prints `No changes made.` and exits 0. The only piped form that works is `bash -s -- --yes --keep-data|--purge`, which the header does not say.

## Evidence
```bash
# uninstall-minecraft-splitscreen.sh:183 / :235
    read -r -p "Keep my data? [Y/n]: " keep_choice
    read -r -p "Are you sure you want to continue? [y/N]: " confirm
```
Reproduced (no controlling terminal, fake `$HOME` with a launcher inside):
```
$ setsid -w bash -c "cat uninstall-minecraft-splitscreen.sh | HOME=$h bash" </dev/null
…
ℹ️  No changes made.
rc=0            # launcher still present
```

## Failure scenario
`curl -fsSL https://raw.githubusercontent.com/…/uninstall-minecraft-splitscreen.sh | bash` prints the target list, then `No changes made.`, exit 0. The user believes the uninstall ran; nothing was removed.

## Suggested fix
Detect "script on stdin" (`BASH_SOURCE[0]` is unset exactly in that mode — the file already relies on this for `SCRIPT_DIR`), read answers from the controlling terminal when one exists, and refuse with an actionable message when there is none. Normal file execution and the existing EOF semantics are untouched.

+# Under curl|bash the SCRIPT occupies stdin, so a plain `read` would consume
+# the next unparsed script line (a blank one → "keep my data" / "No changes
+# made", exit 0 — an uninstall that silently did nothing). BASH_SOURCE is
+# unset exactly in that mode; then answers come from the controlling
+# terminal, and with no terminal at all we refuse rather than guess.
+_SCRIPT_ON_STDIN=false
+[[ -z "${BASH_SOURCE[0]:-}" ]] && _SCRIPT_ON_STDIN=true
+
+# _ask: Prompt for one line of input.
+# Inputs: $1 — prompt string (passed to `read -p`); $2 — name of the variable
+#         to assign the answer to. Globals: _SCRIPT_ON_STDIN (read)
+# Outputs: side effect — sets the named variable. Exits 1 (nothing removed)
+#          when the script arrived on stdin and no terminal is available;
+#          a genuine EOF on a normal stdin still fails `read` under set -e,
+#          exactly as before.
+_ask() {
+    local -n _ask_out="$2"
+    if [[ "$_SCRIPT_ON_STDIN" == true ]]; then
+        if { : </dev/tty; } 2>/dev/null; then
+            read -r -p "$1" _ask_out </dev/tty
+            return
+        fi
+        echo "This script arrived on stdin and there is no terminal to answer its prompts." >&2
+        echo "Re-run with explicit flags, e.g.:  bash -s -- --keep-data --yes   (or --purge / --dry-run)" >&2
+        echo "No changes made." >&2
+        exit 1
+    fi
+    read -r -p "$1" _ask_out
+}

Why this is correct: a curl|bash user in a Konsole gets working prompts (answers come from `/dev/tty`); a headless pipe (`ssh deck 'curl … | bash'`, a script) gets an exit-1 refusal that names the working form (`bash -s -- --keep-data --yes`) instead of a silent no-op; `bash uninstall.sh < answers` and the existing `printf 'n\ny\n' | bash uninstall.sh` test path still read stdin because `BASH_SOURCE` is set. `{ : </dev/tty; } 2>/dev/null` is the correct probe — `-r /dev/tty` is true even without a controlling terminal, the open is what fails. Deliberately NOT changed: the `--yes`/flag paths, the EOF-on-normal-stdin behaviour (`read` still fails under `set -e` as before), and the header claim, which becomes true.

Verified on the patched script: piped + no tty → exit 1, "no terminal" message, nothing removed; piped `bash -s -- --keep-data --yes` + no tty → launcher removed; piped under a pty (`script -qec …`, answering `n` then `y`) → prompts rendered, full uninstall performed.

Validation done: (a) `bash -n` and `shellcheck -S warning` clean; (b) `git apply --check` succeeds from the pristine repo root; (c) `tests/test_uninstall_purge.sh` in a scratch clone: pristine 22/22 → with new tests 23/24 (T9.1 red: `rc=0, launcher present=yes`) → patched 24/24. (Scratch clone under `/tmp` needed F14's fix pre-applied; see F14.)
