## Summary

`tests/test_instance_lifecycle.sh:146` (T4.5: `"pid":99999 … "bwrap_pid":99998`) and `:279` (T4.8: bwrap PIDs `11110 22220 33330 44440`, java PIDs `11111 … 44444`) call the *real* `teardown_instance`, which does `kill -TERM "-${bwrap_pid}"` then `kill -KILL "-${bwrap_pid}"` / `kill -9 "$java_pid"` (`modules/instance_lifecycle.sh:1219,1242,1246`) on whatever the state file names. The fixture comment says "non-existent PID (kill will fail gracefully)", but every one of those numbers is below `kernel.pid_max` (32768 here; 4194304 on 64-bit systemd hosts, where 99998/99999 are reachable too). `tests/test_orchestrator.sh:31-57` documents that this exact shape "has previously SIGKILLed the invoking shell's session" and guards its fixtures above `pid_max`; this suite does not.

## Evidence

```bash

    # Set up: slot 2 active with non-existent PID (kill will fail gracefully)
    cat > "$state_file" <<'JSON'
{"mode":"docked","slots":{...,"2":{"active":true,"pid":99999,...,"bwrap_pid":99998},...}}
# tests/test_instance_lifecycle.sh:278-280
    # All 4 slots active with non-existent PIDs
{"mode":"docked","slots":{"1":{"active":true,"pid":11111,...,"bwrap_pid":11110},"2":{...,"pid":22222,...,"bwrap_pid":22220},...}}
```

```bash
# modules/instance_lifecycle.sh:1219,1242,1246 — the sink
kill -TERM "-${bwrap_pid}" 2>/dev/null || kill -TERM "$bwrap_pid" 2>/dev/null || true
kill -KILL "-${bwrap_pid}" 2>/dev/null || kill -9 "$bwrap_pid" 2>/dev/null || true
kill -9 "$java_pid" 2>/dev/null || true
```

`cat /proc/sys/kernel/pid_max` on the review box: `32768`. Note the `|| kill -TERM "$bwrap_pid"` fallback: if 11110 is not a PGID but is a live PID, the single-PID kill lands instead.

## Failure scenario

Any process group (or process, via the fallback) whose id happens to be 11110/22220/33330/44440/99998/99999 at the moment T4.5/T4.8 run — a Java instance on the Deck, the CI runner's own job tree, the developer's tmux server — gets SIGTERM, then SIGKILL. Low probability per run, unbounded blast radius, and the suite is run on the Deck by the maintainer.

## Suggested fix

Use the `test_orchestrator.sh` guard verbatim: fixture PIDs above `/proc/sys/kernel/pid_max`, refuse to run otherwise. The state-file heredocs become unquoted so the constants expand (the JSON contains no other `$`). Also point `MCSS_GEOM_DIR` at the tmpdir in both tests (review T12 — `teardown_instance` `rm -f`s `${MCSS_GEOM_DIR:-/tmp/mcss-geom}/slotN`, the production cache, on every run; folded in here because it is the same two fixtures).

Why correct: the kernel never assigns a PID/PGID above `pid_max`, so a group or single kill on 4999910..4999944 can only ever fail with ESRCH, which is exactly what the two tests need ("slot becomes inactive even though the process is gone"). It deliberately does NOT mock `teardown_instance`'s kill step — the tests' value is that the real reap path runs end to end against a dead slot.

## Tests

The guard is self-testing: lowering any fixture to a reachable value refuses to run. Verified in the scratch clone by setting `FIXTURE_BWRAP_PID_2=100`:

```
FATAL: fixture PID 100 <= pid_max 32768.
teardown_instance does process-GROUP kills on the state-file
PID; a reachable fixture PID risks hitting a REAL process group
mutant exit=1
```

Mutation for the T12 half (PRINCIPLES #4): drop the `MCSS_GEOM_DIR=` line, pre-create `/tmp/mcss-geom/slot2`, run T4.5 → the file is gone. A follow-up could assert `[[ ! -e /tmp/mcss-geom/slot2 ]] || … ` but the cleaner guard is `export MCSS_GEOM_DIR="$tmpdir/geom"` at suite top for all 16 tests.

## Hardware verification

CI + unit test only: the change is to test fixtures, and the module under test is unchanged. Optional confirmation on the Deck: with a 2-up session running (any mode), `bash tests/test_instance_lifecycle.sh` over SSH → both players keep playing and `ls /tmp/mcss-geom/` still lists `slot1 slot2` afterwards (before the fix, T4.8 removed all four cache files).
