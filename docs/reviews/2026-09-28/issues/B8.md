## Summary
Every Modrinth `version.files[]` entry carries `hashes.sha1`/`hashes.sha512` and every CurseForge `files[]` entry carries `hashes[]` (algo 1 = sha1), in the very responses the installer already parses — but `_modrinth_tier_match` (`modules/mod_management.sh:190-199`) and `match_curseforge_version` (`:329-331`) keep only the URL, and `modules/instance_creation.sh:501` does `fetch_url "$mod_url" "$mod_file" 0` with no check. A truncated CDN body (curl only fails on HTTP status), a stale mirror or a tampered redirect target is written straight into `.minecraft/mods/`, copied to instances 2-4 and loaded into four JVMs. The JDK download in `modules/java_management.sh:217-229` already verifies SHA-256, so the pattern exists in-repo. Merged finding: C5.

## Evidence
`grep -n "hashes\|sha1\|sha512" modules/mod_management.sh modules/instance_creation.sh` -> no hits. `modules/instance_creation.sh:501-506`:
```bash
if fetch_url "$mod_url" "$mod_file" 0 >/dev/null 2>&1; then
    print_success "Success: $mod_name"
else
    print_warning "Failed: $mod_name"
```
Reproduced with T8.3 below against the patched-but-mutated module (`mod_verify_hash` forced to `return 0`, i.e. today's behaviour): a body one byte short of the published sha512 is kept as `Dep.jar`.

## Failure scenario
CDN returns 200 and resets after the headers -> `Sodium.jar` half-written, `fetch_url` returns 0, instance 1 crashes at startup with an opaque zip error and the broken mods dir is copied to instances 2-4. Same path for a deliberately substituted jar: it runs with the user's full account.

## Suggested fix
Record the published hash next to the URL at the two scan sites and at the dependency-resolve site, verify after download, delete + report on mismatch. Sparse `MOD_HASHES` array (same index as `MOD_URLS`); entries without a published hash (external CurseForge deps via `get_curseforge_download_url`, custom-mod paths) install unverified exactly as today, with a debug line.
