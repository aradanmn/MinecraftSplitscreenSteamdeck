title: [F3] Release-asset installer fetches modules from unpinned main with no integrity check
severity: medium
security: yes
type: Bug
related: none

## Summary
`install-minecraft-splitscreen.sh:109` sets `export REPO_REF="${REPO_REF:-main}"` and `:115` builds `MCSS_REPO_RAW_URL=…/${REPO_REF}` from it; `download_modules` (`:199`) then fetches `modules/*.sh` from that URL and the entry `chmod +x`es and `source`s them (`:202`, `:312-327`). `.github/workflows/release.yml:138-146` uploads `install-minecraft-splitscreen.sh` byte-for-byte, so the "v1.2.4" release asset still pulls every module, `minecraftSplitscreen.sh`, `accounts.json`, `add-to-steam.py` and the evsieve patch from whatever `main` is when the user runs it. The entry script and its modules can be from different commits, a release is not reproducible, and a force-push or compromise of `main` is executed by every install of every past release. Transport is HTTPS only; there is no checksum over the module set (contrast the care taken for evsieve in `evsieve_management.sh:60-110`).

## Evidence
```bash
# install-minecraft-splitscreen.sh:109,115
export REPO_REF="${REPO_REF:-main}"
export MCSS_REPO_RAW_URL="https://raw.githubusercontent.com/aradanmn/MinecraftSplitscreenSteamdeck/${REPO_REF}"
```
```yaml
# .github/workflows/release.yml:138-146
      - name: Upload installer script (always)
        uses: softprops/action-gh-release@v2
        with:
          files: install-minecraft-splitscreen.sh
```

## Failure scenario
Tag `v1.2.5` is cut. Two days later a module on `main` renames a function the tagged entry script calls → users who download the v1.2.5 asset get an installer that dies mid-run. Or: someone with push access to `main` (or a hijacked session) edits `utilities.sh` → executed by every installer worldwide, including "old, known-good" release assets.

## Suggested fix
In `release.yml`, bake the tag into the uploaded asset before upload. The step `sed`s the one default line, `grep`s that the substitution happened (a reworded line must fail the job, not ship an unpinned asset), and `bash -n`s the result. An explicit `REPO_REF` in the environment still wins, so branch testing is unchanged.

```diff
--- a/.github/workflows/release.yml
+++ b/.github/workflows/release.yml
@@ -135,6 +135,25 @@
       # build-evsieve job for real without ever touching the GitHub Releases
       # page, so the risky new logic (cargo build, patch/checksum/stamp) can
       # be validated on demand between actual releases.
+      # Pin the uploaded asset to THIS tag. The script's default is
+      # REPO_REF=main, so an unpinned asset fetches modules/*.sh, the
+      # launcher, accounts.json and add-to-steam.py from whatever main is at
+      # run time: the entry script and its modules can come from different
+      # commits, a release is not reproducible, and a later push to main is
+      # executed by every install of an old release. An explicit REPO_REF in
+      # the environment still wins (`${REPO_REF:-<tag>}`), so the documented
+      # branch-testing override keeps working. The grep makes a silent
+      # no-match sed (e.g. after the line is reworded) fail the job instead
+      # of shipping an unpinned asset.
+      - name: Pin REPO_REF in the installer asset to this tag
+        if: github.event_name == 'push'
+        run: |
+          set -euo pipefail
+          sed -i 's|^export REPO_REF="${REPO_REF:-main}"$|export REPO_REF="${REPO_REF:-'"${GITHUB_REF_NAME}"'}"|' \
+            install-minecraft-splitscreen.sh
+          grep -qF 'export REPO_REF="${REPO_REF:-'"${GITHUB_REF_NAME}"'}"' install-minecraft-splitscreen.sh
+          bash -n install-minecraft-splitscreen.sh
+
       - name: Upload installer script (always)
         if: github.event_name == 'push'
         uses: softprops/action-gh-release@v2
```

Why this is correct: `raw.githubusercontent.com/<repo>/<tag>/…` serves the tagged tree, so the asset's modules are exactly the ones the entry script was tagged with; the checkout path (`SCRIPT_DIR/modules`) is unaffected; the `main`-default stays for the README's `wget …/main/install…` dev path, which is documented as tracking `main`. Simulated locally with `GITHUB_REF_NAME=v1.2.5`: the step rewrites line 109 to `export REPO_REF="${REPO_REF:-v1.2.5}"`, sourcing the result yields `MCSS_REPO_RAW_URL=…/v1.2.5` by default and `…/feat/x` with `REPO_REF=feat/x`, and rewording the line makes the step exit 1 at the `grep`. Deliberately NOT changed: the module download itself. Fuller fix (recommended follow-up): have the release job also produce `modules.sha256` (one line per file in `INSTALLER_MODULE_FILES` + `runtime_modules.list`), upload it, and have `download_modules` verify each file against it when `REPO_REF` is a tag — the same shape as `_evsieve_try_prebuilt`. Pair with F9 (validate `REPO_REF`'s syntax).

Validation done: (a) YAML parses, the step's shell block was extracted and executed locally (`set -euo pipefail`) on a copy of the installer, `bash -n` passes on the rewritten file; (b) `git apply --check` succeeds from the pristine repo root; (c) no unit suite covers `release.yml`; `tests/test_installer.sh` still passes 17/17 against the rewritten installer (the change is one default value).

## Tests
Workflow-level: run `release.yml` via `workflow_dispatch` — the pin step is guarded by `if: github.event_name == 'push'`, so add nothing; instead push a throwaway tag (`v0.0.0-pin-test`) to a fork and assert the uploaded asset contains `REPO_REF:-v0.0.0-pin-test`. Unit-level (optional, `tests/test_installer.sh` T7.20): copy the installer, apply the exact `sed` from the workflow with `GITHUB_REF_NAME=vX`, source with `TESTING_MODE=1` and assert `MCSS_REPO_RAW_URL` ends in `/vX`. Mutation: change the `sed` pattern so it no longer matches → the `grep` guard exits 1 (verified locally).

## Hardware verification
Cut a test tag on a fork, download the asset onto the Deck (Desktop Mode) and run `bash install-minecraft-splitscreen.sh --debug` — the debug line `🌐 Repository URL: …/<tag>/modules` proves the pin; complete the install and run `tests/hardware/stage0b_install.sh` then `stage1_modules.sh` so the tagged module set is validated through the real install and launch (PRINCIPLES #3).
