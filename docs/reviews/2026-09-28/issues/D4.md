## Summary
`_evsieve_try_prebuilt` (`modules/evsieve_management.sh:241`) ends with `_evsieve_install_binary "$bin_file"` — an atomic `mv` onto `$TARGET_DIR/bin/evsieve` — and only afterwards does `install_evsieve` run `&& _evsieve_host_verify` (`:555`). A download that passes the stamp and checksum but does not execute on this host (glibc/libevdev ABI, a bad CI build) has already replaced the previously installed, working binary; the code then "falls through to build-at-install", which on a Deck without git/podman/distrobox ends `degraded-no-toolchain` (and with them is broken anyway, #196) — leaving the non-running file in place, executable, with no stamp. The build path has the same install-then-verify order (`:597` → `:604`). `_evsieve_install_binary`'s own docstring (`:478-483`) says the host-exec gate "is a separate step", which is exactly the problem: nothing gates the *replacement*.

## Evidence
`modules/evsieve_management.sh:240-242`:
```bash
    chmod +x "$bin_file" 2>/dev/null || return 1
    _evsieve_install_binary "$bin_file"
}
```
`modules/evsieve_management.sh:555`:
```bash
    if _evsieve_try_prebuilt "$build_root" && _evsieve_host_verify; then
```
`modules/evsieve_management.sh:597-604` (build path, same order):
```bash
    if ! _evsieve_install_binary "$build_root/src/target/release/evsieve"; then
    ...
    if ! _evsieve_host_verify; then
        ... _evsieve_degrade "degraded-host-exec" "$msg"
```
Reproduction: new tests T21/T22 below — a working `0.9.0-old` binary with a stale stamp is replaced by an `exit 1` prebuilt (T21) or an `exit 1` build output (T22) on the current code (`20/22`, both red); the runtime consequence is at `modules/controller_proxy.sh:398-412` (2 s poll, kill, `return 1`) and `instance_lifecycle.sh`'s `_maybe_proxy_swap` falling back to raw binding.

## Failure scenario
Pin bump → stale stamp → prebuilt fetched → `mv` over the good v-old binary → `--version` fails → toolchain absent (or #196) → install ends "degraded" but `$MCSS_EVSIEVE_BIN` is `-x`. At every launch `_proxy_evsieve_bin` says "available", `proxy_start_slot` spawns it, polls 2 s, kills it, returns 1 — for every slot, every launch — and `_maybe_proxy_swap` falls back to raw binding: seamless reconnect silently lost plus a ~2 s launch penalty per player, with no message anywhere near the user. The operator's last-known-good state ("reconnect worked yesterday") is destroyed by an *update attempt that reported it did nothing harmful*.

## Suggested fix
Verify the candidate before it displaces anything: `_evsieve_host_verify` takes an optional path; the prebuilt path checks the downloaded file before `_evsieve_install_binary`, and the build path checks `target/release/evsieve` before copy-out (reporting the existing `degraded-host-exec` token). The post-install `_evsieve_host_verify` stays as the final gate on the installed path.

Why this is correct and what it deliberately does NOT change: the same `--version` probe is used, one encoding (PRINCIPLES #9), now run on the candidate first; every existing status token, message and fall-through is preserved (T11/T19 keep passing unchanged); no rollback machinery (`.prev` copies) is needed because nothing is overwritten until it is known to run. It does not fix #196 (the build fallback itself) — it only stops a failed prebuilt from destroying the last-good install on the way there. Note D5 (pin the prebuilt digest) touches the same function a few lines above; apply D4 first, D5's hunk is adjacent and independent.

Verification performed on a scratch copy: (a) `bash -n` passes; `shellcheck -x` unchanged. (b) `git apply --check` succeeds from the pristine repo root for this diff and the test diff. (c) `tests/test_evsieve_management.sh` → **22/22** on the patched copy (20 existing + T21/T22, ~100 s). Mutation: the new tests against the unpatched module → both red (`20/22`), i.e. the old binary was overwritten.

Run `./install-minecraft-splitscreen.sh`. Expect `Prebuilt evsieve unavailable or unusable — building from source instead.` followed by a `degraded-*` warning (no toolchain on a Deck, or #196), and **afterwards** `~/.local/share/PolyMC/bin/evsieve --version` must still print `1.4.0` with the same `sha256sum` as before.
