# Fix & Verify Plan — Code Review 2026-09-28

Companion to `docs/CODE-REVIEW-2026-09-28.md` (177 findings). This document says
*in what order* to fix them, *how each fix is proven* (unit → mutation → hardware), and
*what one Deck session* has to cover so the hardware time is spent once, not per PR.

Tracking: every Critical/High/Medium finding has its own GitHub issue (with a suggested
diff); Low/Info findings are grouped into one checklist issue per module. All of them are
sub-issues of the tracking issue **`[REVIEW-2026-09-28] Tracking`** — see §7 for the
index. Labels: `review-2026-09-28`, `severity:*`, `security`, `tests`.

---

## 0. Rules for this campaign

These are the repo's own rules (CLAUDE.md / PRINCIPLES.md) applied to a batch of fixes:

1. **One finding, one PR, one issue.** A PR closes its issue with `Fixes #N`. No
   drive-by widening; a Low/Info sweep PR may batch a module's checklist.
2. **Every PR that touches runtime logic ships a test that goes red when the fix is
   reverted** (PRINCIPLES #4). The issue names the mutation; the PR description quotes
   the red run.
3. **Nothing on the launch, controller or display path is "done" until it has run on a
   Deck through the real Steam launch** (PRINCIPLES #3). Unit + probe are necessary, not
   sufficient. The hardware pass is batched in §5 so it is done once per phase.
4. **Behaviour changes that could regress a working session ship flag-gated, default
   OFF**, and flip in a separate one-line PR after the hardware pass (PRINCIPLES #2).
   In this plan that applies to: D1 (dock confirm-across-reads), A3/A4/A6 (mode
   transitions), B4 (startup reap of recorded PIDs), E6 (dex timeout).
5. **No `pkill`/`killall`/name-matched kills anywhere in the fix**, including tests
   (PRINCIPLES #7). Three findings (A1, A7, E9, T1) *remove* such kills; none may add one.
6. **CI must be able to see a regression before the big fixes land** — Phase 0 is first.
7. Fix order inside a phase is by user impact; a lower-phase item never waits on a
   higher-phase one unless listed as a dependency.

## 4. Verification ladder (what "proven" means per layer)

| Layer | Tool | Proves | Cannot prove |
|---|---|---|---|
| Static | `bash -n`, `shellcheck`, `py_compile` | Syntax, obvious quoting | Any behaviour |
| Unit | `tests/test_*.sh` (CI) | The function does what the test says | Integration between monitor → orchestrator → launch |
| Mutation | Break the code, re-run | The test actually guards the logic | Coverage of untested paths |
| Probe | `tests/probe-*.sh` (Deck, Desktop Mode) | One subsystem live (evsieve, KWin, gamescope) | The Steam-launched session |
| Session | Steam shortcut launch + `tests/hardware/run_all.sh stageN` | The real thing, as a player sees it | Timing-dependent races unless soaked |
| Soak | 20–30 min docked 4-up with hotplug/dock events | Races, leaks, orphans | — |

A finding is closed when it has reached the highest layer its issue names.

## 6. Rollback

Every runtime change is either one hunk (A1, E1, B1's reorder) or flag-gated. Rollback is
`git revert` of the PR; for a flipped flag, set it back to 0 in Steam launch options
(`MCSS_DOCK_CONFIRM_READS=1 launchFromPlasma`) without a redeploy. Installer changes are
re-runnable (the installer is idempotent by design; after Phase 4 it is also atomic).
